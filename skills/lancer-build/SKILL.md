# Lancer build advice and guides

1. Ask how the player wants to build: **guided walkthrough** or **autonomous draft**. Explain the choice before they decide: guided means frequent questions, plain-language explanations of frames and available gear, and a decision together at each LL; autonomous means the player gives goals and constraints, then you research and draft the progression for review, asking only when a missing choice blocks it. Neither mode publishes or changes their COMP/CON export without permission. Do not assume a mode.
2. Ask which pilot the build is for: an existing named roster pilot or a new pilot not yet on the main roster. For an existing pilot, confirm the roster identity and current pilot page; for a new pilot, ask their name/callsign and keep the draft separate from the roster until the player approves adding them. Do not guess a page from a similar name. Ask whether the player already knows which traits they want. If yes, capture them in their own words and ask which matter most when choices conflict. If no, ask what team role they want; offer striker, defender, controller, support, or scout as examples if useful. Ask whether they have a license/frame goal (for example, Goblin III and Swallowtail III), or want help learning what frames and unlocks are available. For the latter, describe relevant options and their playstyles in plain language before asking them to choose. Then ask for current LL and fielded COMP/CON export if one exists, teammates, allowed catalogs, respec permissions and GM rulings. Preserve the fielded build as history; label hypothetical respecs. Never overwrite the export.
3. Read existing guide and export before proposing changes. Treat export as current-state authority, then the GM's source restrictions. Read rules, talent ranks, frame, equipment and core bonus text in the installed catalog. Use `massif-press/lancer-data` `lib/*.json` and optional supplement subset (`frames.json`, `weapons.json`, `systems.json`, `talents.json`). Track source name/version and exact ID per claim. Do not conflate license rank with LL or unlocked weapon with installed weapon.
4. Compare at least a conservative current-frame path and alternatives the player wants. For each, check actions, reactions per round, triggers consumed by allies versus by pilot, Sensors, weapon range, license order and what replacing a talent delays. Cite relevant rank text and mark interpretations for GM confirmation. Do not claim community consensus without evidence.
5. In guided mode, work one LL at a time. At each level, explain the unlocked license options and what their frames, weapons and systems actually do; ask which mech they want to pilot now or work toward, which subsystem/weapon/talent appeals, and how they expect their turn and team interactions to play. Confirm the pilot's trigger +2, HASE +1, talent rank, license rank, and core bonus when due; if the table uses Bonds, confirm the bond separately from triggers and track its powers by XP, not LL. Then confirm the complete mech print: frame, each installed system and its SP, total used/capacity, each weapon in its actual mount, and installed AI limits. Distinguish an unlocked item from an installed one; check what must come off when something new goes on. Show changes from the previous LL, including any gear removed or restored. Unspent SP is allowed; ask before filling it with optional gear, and never remove a preferred system just to preserve a filler. Do not advance with a proposed loadout presented as confirmed. Offer a small set of relevant choices with pros and costs instead of dumping the catalog. If the player has no preference, recommend one and ask before locking it in. Adjust question depth to their answers; guided means patient, interactive help, not one giant questionnaire. In autonomous mode, draft the full path from stated goals and constraints, then show assumptions and tradeoffs for review before treating it as chosen. Let the player switch modes at any time.
6. Generate a JSON skeleton, one complete print per LL. Commands from repo root:

   ```sh
   node tools/pilot-build.cjs scaffold --pilot 'CALLSIGN' --frame FRAME_ID --data /path/to/lancer-data/lib [--supplement /path/to/subset] > /tmp/pilot-build.json
   node tools/pilot-build.cjs page /tmp/pilot-build.json --data /path/to/lancer-data/lib [--supplement /path/to/subset] > /tmp/pilot-build.md
   node tools/pilot-build.cjs check /tmp/pilot-build.json --data /path/to/lancer-data/lib [--supplement /path/to/subset]
   ```

   Fill `levels[0..12]`: `license` is `Goblin I` etc (one gained rank per LL), `frame`/`systems`/`weapons`/`talents` are catalog IDs, `systemsScore` is the System HASE score, `coreBonus` may be `Improved Armament`, and `mounts` list the actual frame mount slots. `talents` repeats an ID once per acquired rank, with three ranks total at LL0 and one added each level. Record HASE totals, pilot triggers, Bonds (when used), and player-confirmed equipment choices in the guide as well; do not assume the checker models all of these. Page is an editable Markdown skeleton, not prose generated by the checker. It can render incomplete prints. `check` requires complete prints and reports mechanical failures.
7. Write prose in the page skeleton: what changed at each LL, core loop, action/reaction contention, ally triggers, costs of each alternative, relevant text citations and uncertain GM rulings. For multiple paths, keep independent JSON files and label each page or combine their checked sections manually. Check each path before publishing. Guide pages are one full-width column with build tabs and an LL0–LL12 timeline that wraps to multiple rows (no horizontal scroll). Do not add a sidebar or contents rail; the tabs and timeline are the navigation. Add no status prose ("chosen build", "older alternative", "pending rebuild") to subtitles, intros or tab panels; the build's own levels are the content. Keep licensing clear for any reproduced source text. The intended destination is that pilot's page, not another pilot's guide. Before posting, show the player the exact target page and draft and ask permission. For a new pilot, ask separately before adding them to the main roster; a build draft alone does not create a roster entry or publish a page.
8. Script checks catalog IDs, license order, talent count/rank caps, frame and item unlocks, SP formula and ordinary mount size. It does **not** prove optimization, rules-trigger interpretation, core bonus timing, HASE acquisition schedule, AI uniqueness, limited gear, unique tags, integrated equipment, special mount effects, Bonds, pilot triggers, or COMP/CON export parity. Verify those against rule text and COMP/CON yourself. Check SP at every LL as frame base + floor(Systems/2) + GRIT, count SP on mounted weapons too, and verify each mount's legal combination after core bonuses. Confirm that the authored page reflects the validated print rather than an older build. Never turn a passing script into a blanket legality claim.
9. AI slots: a system's SP cost and its AI-slot use are separate. Servant-Class NHP costs 0 SP but still counts toward the one-AI limit. Only Enlightenment-Class NHP (Technophile III) and the Dustgrave Unstable NHP (Iconoclast I) say they do not count; The Lesson of Shaping adds one regular AI slot. Read each AI system's own text before counting slots.
10. Check every allowed source before recommending talents, not just the core book: Long Rim (Black Thumb), Dustgrave (Iconoclast), Karrakin (House Guard, Bonds) and the others. Ask whether each supplement is allowed at the table, and say so when a recommendation depends on one.
11. Ability panels: put current numbers where the player reads them. Show Speed, Tech, Weapon, Sensors, Evasion, E-Defense, HP and Heat on a stat board with a small note for anything that changed since the last level, then a short "since LL" list of new and removed gear, then one-line rows that expand to labelled lines (ROLL, RANGE, DAMAGE, LIMIT), one value per line. Derive every number from the same build row that sets SP and HASE; never copy numbers into prose. Set cards by name, never by array position, and keep a check that fails when a card holds another card's text.
12. Test before publishing: after changing generated guide HTML, break one value on purpose and confirm the guide check fails, then restore it. Preview on a phone-width screen; a screenshot that comes back blank is not a pass.

The script reads supplied local catalog files and writes only stdout/stderr. No auto-downloads, repo writes, commits or pushes. Source: https://github.com/massif-press/lancer-data .
